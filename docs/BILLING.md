# ЮKassa: запуск платёжного API

Сервис размещается на отдельном сервере владельца приложения, не на VPS покупателя. Он не получает SSH-пароли, SSH private keys и VPN-конфигурации. Получает SHA256-привязку сервера, email для чека и идентификатор заказа.

## Настройка

1. Создайте магазин ЮKassa, настройте фискализацию, оферту и возвраты.
2. Сгенерируйте Ed25519-ключ: `cargo run -p myserv-billing -- keygen`. Вывод содержит **секрет**. Выполняйте локально в безопасной консоли, перенесите приватное значение в хранилище секретов; не публикуйте вывод и не запускайте keygen в CI.
3. Задайте переменные серверу:

| Переменная | Значение |
| --- | --- |
| `YOOKASSA_SHOP_ID` | shop ID магазина |
| `YOOKASSA_SECRET_KEY` | секрет магазина, только backend |
| `MYSERV_SIGNING_KEY` | приватные 32 байта Ed25519, base64url без padding |
| `MYSERV_DATABASE` | абсолютный путь к SQLite в каталоге с правами 0700 |
| `MYSERV_RETURN_URL` | ваш HTTPS-адрес страницы возврата «Вернитесь в MyServ» |
| `MYSERV_VAT_CODE` | код ставки НДС для вашей услуги, по документации ЮKassa |
| `MYSERV_LISTEN` | по умолчанию `127.0.0.1:8090`; внутри Docker `0.0.0.0:8090` |
| `MYSERV_ALLOW_TEST_PAYMENTS` | отсутствует/false для production; true **только** в изолированном тестовом окружении с отдельной парой ключей |

4. `cargo run --release --locked -p myserv-billing`. Поставьте HTTPS reverse proxy перед API, ограничение частоты запросов и размера тела. Не публикуйте порт SQLite/прямой HTTP. Нельзя включать логирование Authorization или request body.
5. В клиент при сборке передайте `MYSERV_BILLING_URL` и публичный `MYSERV_ISSUER_PUBLIC_KEY` (из keygen). Пересоберите приложение при смене ключа издателя. На клиент секрет ЮKassa не передаётся.

Контейнер: `docker build -f services/billing/Dockerfile -t myserv-billing .`. В облачной среде добавьте `--secret id=proxy_ca,src=/etc/ssl/certs/ca-certificates.crt`. Пример `services/billing/compose.yaml` слушает только loopback; секреты загружаются из окружения оператора. Резервируйте SQLite вместе с WAL; приватный ключ подписи — отдельно.

## Протокол

* Клиент генерирует UUID v4 заказа и 256-битный capability-token. `POST /v1/payments`: JSON `{id, server_binding, receipt_email}`; `Authorization: Bearer <64 hex characters>`.
* Цена определяется сервером: **199.00 RUB**, capture=true. Клиент не может изменить сумму. Чек содержит одну услугу.
* UUID передаётся ЮKassa как `Idempotence-Key`. В SQLite сохраняются binding, хеш capability и ID платежа. Повтор не создаёт отдельный платёж.
* `GET /v1/payments/{id}` с тем же Authorization заново получает состояние из ЮKassa. Только `succeeded`, `paid=true`, точная сумма/валюта и совпадающие metadata дают лицензию. Production отклоняет `test=true`.
* Redirect в приложение, письмо, скриншот или непроверенный webhook не подтверждают оплату. Webhook endpoint не нужен для этой версии: используется проверка через API по запросу клиента.
* Лицензия Ed25519 содержит продукт, заказ, SHA256-привязку IP+SSH host key и сумму. Установщик проверяет подпись до изменения VPS.

## До коммерческого запуска

Прогоните test shop: успех, отмена, задержка, повторы POST, перезапуск клиента/API, временная ошибка провайдера, другой сервер, возврат. Затем выполните контролируемый production smoke с разрешения владельца магазина. После возврата офлайн-лицензия автоматически не отзывается; нужна отдельная политика и серверная проверка при расширении продукта.

В мобильных store-сборках покупки отключены. Добавьте StoreKit/Play Billing с проверкой receipt на backend или оформите допустимый для выбранного магазина и региона внешний платёжный канал. ЮKassa остаётся готовым провайдером для Windows и согласованной прямой дистрибуции. Не размещайте приложение в магазине до проверки этой модели.

Если создание платежа имело неизвестный результат и provider ID не был сохранён, после 23 часов API останавливает автоматические повторы. Это защищает от нового списания за пределами окна идемпотентности провайдера. Оператор должен найти платёж по metadata `order_id` в ЮKassa и восстановить provider ID; нельзя просто удалять заказ и предлагать платить ещё раз.
